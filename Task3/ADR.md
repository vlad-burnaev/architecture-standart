#### **Архитектурные решения:**

**1. Микросервисная архитектура для функционала депозитов в интернет-банке**

В рамках задачи открытия депозитов интернет-банк переводится на микросервисную архитектуру. Это позволяет:
- Независимо развертывать и масштабировать компоненты
- Изолировать новый функционал от монолитного ядра
- Использовать современные технологии без изменения ядра подрядчика

**2. Промежуточный слой между интернет-банком и АБС**

Для защиты перегруженной АБС от прямой нагрузки создается промежуточный слой:
- **Сервис депозитов** - обрабатывает заявки из интернет-банка, буферизует их и отправляет в очередь
- **Очередь сообщений** - асинхронная обработка заявок, защита от пиковых нагрузок
- **Сервис ставок** - кэширует ставки для быстрого доступа, синхронизируется с АБС

**3. Кэширование справочных данных**

Для решения проблемы медленной загрузки справочных данных (>1 сек) реализуется:
- Кэш ставок по депозитам в сервисе ставок
- Периодическая синхронизация с АБС
- Быстрый отклик для пользователей (миллисекунды)

**4. Асинхронная обработка заявок**

Заявки из интернет-банка обрабатываются асинхронно:
- Клиент получает немедленное подтверждение о принятии заявки
- Заявка попадает в очередь для обработки АБС
- Менеджер бэк-офиса обрабатывает заявки из очереди
- СМС-уведомления отправляются после обработки

**5. Технологический стек**

- **Интернет-банк (новый сервис депозитов)**: ASP.NET Core (совместим с .NET Framework), MS SQL Server
- **Сервис ставок**: ASP.NET Core, MS SQL Server (кэш)
- **Очередь сообщений**: MS SQL Server Service Broker (совместимо с существующей инфраструктурой)
- **АБС**: Oracle, PL-SQL (существующая система)
- **Система кол-центра**: Java Spring Boot, PostgreSQL (существующая система)
- **Сайт**: PHP, React.js (существующая система)

**6. Интеграция с существующими системами**

- **СМС-уведомления**: через существующий СМС-шлюз и АБС
- **Система кол-центра**: интеграция через API для передачи заявок
- **АБС**: интеграция через очередь сообщений и API для чтения данных

**7. Безопасность**

- HTTPS для всех внешних соединений (TLS 1.3)
- Шифрование данных при передаче между системами (AES-256)
- Разделение доступа к данным (бэк-офис депозитов и кредитов)

**8. Отказоустойчивость**

- Резервный ЦОД для интернет-банка
- Репликация данных между ЦОД
- Балансировка нагрузки между серверами
- Мониторинг и автоматическое переключение при сбоях

### **Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

**Альтернатива 1: Прямая интеграция интернет-банка с АБС**

**Описание:** Интернет-банк напрямую обращается к API АБС для создания заявок и получения данных.

**Почему не выбрано:**
- База данных АБС уже перегружена
- Прямые запросы могут поставить под угрозу работоспособность банка
- Нет защиты от пиковых нагрузок
- Нарушает требование NFR9

**Альтернатива 2: Использование Kafka для очередей сообщений**

**Описание:** Использование Apache Kafka для асинхронной обработки заявок.

**Почему не выбрано:**
- Текущая версия платформы интернет-банка несовместима с Kafka
- Требует дополнительной инфраструктуры и экспертизы
- Для MVP достаточно более простого решения (MS SQL Service Broker)

**Альтернатива 3: Полный рефакторинг интернет-банка на микросервисы**

**Описание:** Перевод всего интернет-банка на микросервисную архитектуру.

**Почему не выбрано:**
- Слишком масштабный проект для MVP
- Высокие риски и сроки реализации
- Достаточно перевести только функционал депозитов

**Альтернатива 4: Хранение ставок в отдельной БД интернет-банка**

**Описание:** Создание отдельной базы данных для ставок в инфраструктуре интернет-банка.

**Почему не выбрано:**
- Дублирование данных и необходимость синхронизации
- Риск рассинхронизации данных
- Лучше использовать единый источник истины (АБС) с кэшированием

**Недостатки, ограничения, риски**

**Недостатки:**
1. **Сложность синхронизации данных**: Кэширование ставок требует механизма синхронизации с АБС, что может привести к задержкам в обновлении данных
2. **Дополнительная инфраструктура**: Новые сервисы требуют дополнительных ресурсов и поддержки
3. **Зависимость от очереди**: Асинхронная обработка через очередь может привести к задержкам в обработке заявок при проблемах с очередью

**Ограничения:**
1. **Ограничения АБС**: АБС может масштабироваться только вертикально, что ограничивает возможности масштабирования всей системы
2. **Технологическая совместимость**: Необходимость использования совместимых технологий ограничивает выбор решений
3. **Экспертиза команды**: Ограниченная экспертиза в новых технологиях может замедлить разработку

**Риски:**
1. **Риск перегрузки АБС**: Даже с промежуточным слоем существует риск перегрузки при большом количестве заявок
2. **Риск рассинхронизации данных**: Кэширование ставок может привести к отображению устаревших данных
3. **Риск недоступности сервисов**: Новые сервисы могут стать точкой отказа, требуется тщательное проектирование отказоустойчивости
4. **Риск задержек в обработке**: Асинхронная обработка может привести к задержкам, что ухудшит пользовательский опыт
5. **Риск сложности поддержки**: Микросервисная архитектура увеличивает сложность поддержки и мониторинга

**Меры по снижению рисков:**
- Реализация мониторинга и алертинга для всех сервисов
- Настройка автоматического масштабирования и балансировки нагрузки
- Реализация механизмов повторных попыток и обработки ошибок
- Регулярная синхронизация кэша с АБС
- Тщательное тестирование под нагрузкой
- Постепенное внедрение с возможностью отката
